# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Shift is a Gmail client for macOS: a Rust core (Tauri 2) with a vanilla TypeScript UI. Setup, OAuth credentials, the account layout and the shortcut table are in `README.md`.

## Commands

```sh
bun run demo                      # fake mailbox (SHIFT_DEMO=1), no Gmail; use this for UI work
bun run tauri dev                 # real Gmail; needs GOOGLE_CLIENT_ID/SECRET in .env.local
bun run build                     # tsc + vite (the frontend typecheck)
bun test                          # all TS tests; one file: bun test src/keys.test.ts
bun run format                    # Prettier, TypeScript and public/*.js only (.prettierignore); format:check is one of the checks
cd src-tauri && cargo test        # one test: cargo test label_filtering
cd src-tauri && cargo clippy --all-targets
cd src-tauri && cargo fmt         # rustfmt defaults; `cargo fmt --check` is one of the checks
cd src-tauri && cargo audit        # advisories; .cargo/audit.toml lists the Linux-only ones ignored for the Mac build
cd site && bun run dev           # the Astro site (home, roadmap, changelog, privacy, terms) with hot reload
cd site && bunx wrangler dev     # the built site plus the early access Worker, local KV and R2
cd site && bunx wrangler deploy   # manual deploy to getshiftmail.com (needs `gh` signed in); pushes to main that touch site/ deploy on their own via Cloudflare Workers Builds
scripts/release.sh [--publish] "notes"   # signed, notarized universal build; --publish puts Shift.dmg in R2 and deploys the update feed
```

The site's changelog is one Markdown file per release in `site/src/content/changelog/`. The roadmap page lists GitHub Issues labelled `roadmap: now`, `roadmap: next` or `roadmap: later` (titles only), read at build time.

Run all the checks (`bun test`, `bun run build`, `bun run format:check`, `cargo fmt --check`, `cargo test`, `cargo clippy`) before calling a change done. `tauri dev` and `demo` both need port 1420, so only one can run at a time. To release, bump `version` in `tauri.conf.json`, commit, and run `scripts/release.sh`: it refuses uncommitted changes, runs the checks, stages in `site/.release` (never in `site/public`, whose files Cloudflare would serve ahead of the R2 feed), and tags `v<version>` on publish. Release builds check `updates/latest.json` (served from R2 by the Worker) at launch and every six hours and offer a restart. The script's one-time Keychain and signing-key setup is in its header. `build.rs` bakes the OAuth client in at compile time, so a changed `.env.local` takes a Rust rebuild.

Before writing or changing Rust, load the `anthropic-skills:rust-best-practices` skill and follow it. `Cargo.toml`'s `[lints.clippy]` enforces part of it (no `unwrap()` outside tests, `perf`, redundant clones), and an exception takes `#[expect(..., reason = "...")]`, not `#[allow]`. The rest is judgement: borrow rather than clone, `&str` and `&[T]` parameters where nothing needs ownership, `anyhow` with `?` and `.context()`. Run `cargo fmt` after editing Rust. The commit that first formatted it is in `.git-blame-ignore-revs`.

## Architecture

**The local cache comes first.** The UI reads only from SQLite through Tauri commands and never waits on Gmail. Writes such as `modify` change the local DB, emit `mail-changed`, then call Gmail. If the Gmail call fails, the command re-fetches the thread to undo the local change. The frontend listens for `mail-changed` and re-renders (`refresh` in `main.ts`). New commands that change mail should follow the same order.

**Sync** (`lib.rs`): a loop runs `sync` every `general.syncSeconds`, which it reads from the settings file. Accounts sync in parallel. Each syncs incrementally from the `history_id` kept in its `meta` table; a history fetch saves the new `history_id` only after it succeeds, so a failed sync replays instead of skipping changes. With no `history_id`, or when Gmail returns 404 for an expired one, `full_sync` lists the mailbox into a `backfill` queue in `meta` and saves the cursor at once; `backfill` then works through it, putting failures at the back. Each tick spends at most `tick_budget` quota units on background fetching (60% of Gmail's 6,000 a minute, scaled to the interval; a thread costs `METADATA_COST` or `FULL_COST`), history bursts beyond that join the backfill queue, and body prefetch gets what's left. Older mail beyond the first listing comes in a page at a time through `load_more`, when a list is scrolled to its end. Bulk label changes (multi-select, Undo of one, Clean up) go through `modify_many`: one `messages.batchModify` per account instead of a call per thread; Trash still goes thread by thread. Every label change goes into `pending_ops` before Gmail is asked and leaves it once Gmail takes or refuses it, so one that can't get through (offline, outages: `gmail::is_transient`) or is cut off by quitting is replayed at the start of each sync, in order; a thread with pending changes isn't overwritten by a fetch. The Inbox unread count adds `inbox_unread_extra`, Gmail's unread threads beyond the cache. A thread's labels in `thread_labels` come from its messages outside Trash and Spam (plus `TRASH`/`SPAM` from any message), and `threads.live` says whether any message is outside them, so one trashed reply doesn't hide the conversation; lists other than Trash and Spam show live threads only. Message bodies are prefetched only once the queue is empty. After a history fetch, `notify_new_mail` announces unread Inbox mail newer than the `notified_at` watermark. `mail-changed` is emitted only when something was fetched. Sync failures emit `sync-error`.

**Commands**: every Tauri command in `generate_handler!` must also be listed in `build.rs` (the app manifest) and as `allow-<name>` in `capabilities/default.json`, or the window is refused it at runtime.

**Accounts**: each `Account` in `State` has its own SQLite connection, cached access token and sync lock. Its refresh token lives in the Keychain (`auth.rs`). Commands take `account: String` for one account, or `accounts: Option<Vec<String>>` for a list. `State::scope` turns `None` into the unified view, which leaves out accounts whose `accounts.<email>.unified` setting is `false`. Threads returned to the UI carry their `account`, and the frontend passes it back on every action.

**Demo mode** (`demo.rs`): two in-memory accounts are seeded on each launch with fixtures in Gmail API format, which go through the real parser and `db` code. Every command that reaches the network checks `s.demo` first and returns early or works only on the cache. A new network command needs the same check.

**Settings**: one JSON document. `src/settings.ts` holds `DEFAULTS`, merges the saved file over them, applies changes right away via listeners and dotted paths (`setSetting("appearance.theme", …)`), and saves about 300 ms later through `set_settings`. Rust reads the same file (`settings.rs`) for backend values such as the sync interval and unified-view opt-outs, so a setting the backend uses must have the same key on both sides. AI provider keys go to the Keychain, not the JSON file. `settings-ui.ts` builds the settings window.

**Frontend**: `main.ts` holds the app state as module-level variables (`accounts`, `scope`, `mailbox`, `threads`, `selected`) and renders by setting `innerHTML`. Escape interpolated text with `esc()`. Email HTML is sanitised with DOMPurify (`cleanEmail`) before it goes into the reader's iframe. The frame is sandboxed without `allow-same-origin`, so it can't reach the app; its CSP allows one script, `public/email-frame.js`, which evens out the text, folds quoted history and reports its height, clicked links and key presses by `postMessage` (the app's `message` listener matches the frame by its window). With remote images off, the CSP also blocks every network load. Hovering a link shows its address in `#link-status`. Inline `cid:` images are sent into the frame the same way. The other files are small modules with their own tests:
- `keys.ts`: the action list and default bindings. Settings can remap every binding.
- `compose.ts`: the editor's extensions, the plain-text version of the body (`docToText`) and the HTML as sent (`emailHtml`). `editor.ts` builds the Tiptap editor and its format bar.
- `attachments.ts`: file chips, icons and sizes for the reader and the composer.
- `recipients.ts`: the recipient chips.
- `palette-match.ts`: ⌘K ranking.
- `toast.ts`: the one toast at the bottom of the window: `toast(msg, { action, ms, icon })` returns a handle to update or close it.

The keyboard handler skips single-key shortcuts while focus is in an `input`, `textarea` or `[contenteditable]`. Any new editable element needs to be covered by that check too. Icons are Tabler (the 300-weight webfont, `ti ti-*` classes). Render named icons with `iconHtml`/`iconClass` from `src/icons.ts`, which maps the older names still used in data.

**Composer**: replies, forwards and new emails open in the `#composer` dialog (replies and forwards open inline under the thread when `composer.replyIn` is `inline`). The body is a Tiptap editor (vanilla core API, StarterKit). Replies and forwards carry the original as a `quote` node (`compose.ts`): one block holding its cleaned HTML and text, shown as a sandboxed preview and folded behind •••, and put back whole by `emailHtml` as `blockquote.gmail_quote`, so its images, tables and styles survive. Reopened drafts parse that blockquote back into the node. The signature sits in the editor above the quote: a text signature as paragraphs, an HTML one as a `signature` node that shows a sandboxed preview and is swapped for the real HTML by `emailHtml` at save and send time, so signature markup never runs in the app. Drafts and sends carry `html` (from `getHTML`) and `body` (from `docToText`). Files attach with the paperclip or by drag and drop (the window sets `dragDropEnabled: false`, so the webview gets the drop). They travel as base64 in `Draft.attachments`, with a 25 MB total. Forwarding attaches the original's files. Drafts save to Gmail about 1.5 s after typing stops (15 s with over 1 MB of files, since every save re-uploads them). Sending a saved draft uses `drafts.send`. Undo send is a scheduled send due in a few seconds (below), so it survives a quit or restart, and Undo cancels it. Closing a composer whose draft can't be saved reopens it instead of dropping it, and ⌘Q waits (up to 5 s, `before-quit` then `quit_now`) for an open draft to save. Opening an email in Drafts finds its Gmail draft (`find_draft`) and reopens it in the composer.

**Send later**: Gmail has no scheduled send. `schedule_send` saves the `Draft` JSON (plus opaque `ui` data for reopening the composer) in the per-account `scheduled` table, next to its Gmail draft, and refuses without a draft id: sending a saved draft is idempotent (a repeat gets 404), a raw send isn't. A timer (`send_when_due`) sends it on time; the sync loop catches anything missed. `sync` calls `send_due` for every account each tick, in demo mode too, and sends through the same `deliver` as `send`. A 404 drops the row; other errors are saved on the row (`error`, shown in the Scheduled list with "Sending…" for a claimed row) and retry on the next tick, and a failing row doesn't stop the others. The sender claims a row (`db::claim`, the `sending` flag) before sending; `reschedule` refuses a claimed row, so a cancel can't race a send. Claims are cleared on launch. The Scheduled mailbox (`"SCHEDULED"` in `main.ts`) is built from `scheduled` rows, not Gmail threads, so `openThread`, `act` and the list's right-click menu branch on it. Quick times come from `src/schedule.ts`.

**AI** (`ai.rs`): the user's own provider account, set in Settings → AI (one Keychain key per provider). A default provider and model, which the two task kinds (`ai::Task::Writing`, `ai::Task::Sorting`, settings `ai.tasks.*`) can each override with their own; `ai::config(dir, task)` resolves which. `ai::complete` sends one request to Anthropic's Messages API (raw HTTP, `anthropic-version: 2026-10-21`, structured output through `output_config.format`) or to any OpenAI-compatible chat API; the prompts are constants in `ai.rs`. Features: `ai_rewrite` and `ai_draft_reply` (the composer's AI menu, which sends the conversation as text), `auto_label` after a sync with new mail, read or not, in its own task beside the sync and 40 emails per AI request, and `ai_label_inbox` on demand for the newest Inbox mail (only labels the user described in `ai.labelRules`; added labels are recorded in the `ai_labels` table so the reader can show and undo them), and `ai_cleanup` (`src/cleanup.ts`, suggestions only: the user archives; it runs in the background with a corner card while sorting). Anything that sends mail content to the provider must stay listed in the site's privacy policy.

**Gmail client** (`gmail.rs`): REST over `reqwest` with backoff on 429/5xx. MIME bodies and attachment details are parsed here. Attachment details go in the `attachments` table, keyed by message. The bytes stay in Gmail and are fetched on demand (`attachment_data`, `open_attachment`), unless Gmail sent them inline. Outgoing mail is built with `mail-builder` (`build_message` in `lib.rs`). Messages over about 3 MB go through Gmail's upload endpoint, because JSON bodies are capped at about 5 MB.

Each account database carries a schema version (`PRAGMA user_version`, `db::VERSION`): a schema change bumps it and adds an `if version < N` step to `db::open`, which runs in one transaction. A database that can't be opened at launch is renamed `.broken` and reported, and the other accounts open. Gmail-facing code is tested against `fake_gmail.rs`, a local stand-in server the real client talks to in tests.

Notes for later work are written in code as `// shortcut: <limit>, <when to upgrade>`. Grep for `shortcut:` to see the known limits.
